# Not enough disk for the next change

## What happens

A host was sized for what it ran when it was built. The next change (container images, a new data
store, logs, a time-series database) doesn't fit and fails halfway: an image pull that runs out of
space, a database that can't write. Thin-provisioned storage adds a second limit: the pool can run
out while every volume still looks half empty.

## How to spot it

- Before a change: `df -h /` against the size of what's coming (`docker images`, retention settings).
- PromQL: `node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}`;
  the thin pool: `pve_disk_usage_bytes{id=~"storage/.*"} / pve_disk_size_bytes`

## How to fix

Grow the volume online (`pct resize <ct> rootfs +<n>G` for an LXC; `qm resize` and growpart for a
VM), then check the thin pool still has room. Clean what's reclaimable (`docker image prune`).

## How to prevent

Bound retention and caches explicitly (Prometheus `--storage.tsdb.retention.size`), and check
headroom when planning any change that adds data or images. DiskFillingUp and StoragePoolAlmostFull
warn before it's urgent.
