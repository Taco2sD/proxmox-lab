# SambaDatabaseErrors

## What it means

Samba's own consistency check of the AD database (`samba-tool dbcheck --cross-ncs`,
read-only, daily at 04:30 on dc01: roles/samba_health) found real errors
(`lab_samba_dbcheck_problems{kind="error"}`), or hasn't completed for two days. dc01 is
the lab's only domain controller: its database holds every account, group, computer,
DNS name and DHCP registration, and there's no second DC to replicate a good copy from.

Stale links (`kind="stale_link"`: a group's inactive member link to a workstation deleted
afterwards) don't fire this alert. Each deleted workstation leaves one, and Samba keeps
it for the tombstone lifetime (180 days). They show on dc01's Machine dashboard and
clear with the same fix as below.

## First five minutes

1. See exactly what it found (read-only, ~3 s): `sudo samba-tool dbcheck --cross-ncs` on
   dc01. Lines starting `ERROR:` are what fired the alert.
2. If the check itself failed (`lab_samba_dbcheck_success == 0`):
   `journalctl -u lab-samba-dbcheck -n 50` and `systemctl status samba-ad-dc`.
3. Are sign-ins and DNS still fine? The Service checks panel (LDAPS, Kerberos, DNS) on the
   Lab overview, and `getent passwd jrhodes` on a workstation.

## Common causes

- Links left behind by deleted objects that Samba didn't mark as plausible leftovers.
- An interrupted write (dc01 lost power or was killed mid-transaction).
- A hand edit with `ldbmodify`/`ldbdel` (as for the stale DNS records in KB-0029) that
  left a backlink out of step.

## Escalate / fix

1. Make sure last night's backup of dc01 exists before changing anything: on pve01,
   `ls -l /var/lib/vz/dump/vzdump-qemu-105-*` (roles/pve_backups). If it doesn't, take one
   first: `vzdump 105 --storage local --mode snapshot --compress zstd`.
2. Fix: `sudo samba-tool dbcheck --cross-ncs --fix --yes`, then run it again without
   `--fix` and expect `Checked N objects (0 errors)`.
3. Refresh the metric: `sudo systemctl start lab-samba-dbcheck.service`.
4. An error dbcheck can't fix, on the only DC: restore dc01 from its backup
   (`qmrestore`), which loses AD changes since 03:30. Not a step to take alone.
