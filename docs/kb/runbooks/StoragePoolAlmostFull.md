# StoragePoolAlmostFull

## What it means

A Proxmox storage has been over 85% used for 10 minutes. `local-lvm` is an LVM thin pool:
VM disks are promised more space than exists, and when the pool fills, every VM writing
to it stops.

```promql
pve_disk_usage_bytes{id=~"storage/.*"} / pve_disk_size_bytes > 0.85
```

## First five minutes

1. On pve01: `pvesm status` and `lvs -o lv_name,lv_size,data_percent,metadata_percent pve`
   (the pool is `pve/data`; its metadata filling up is as bad as its data).
2. The biggest disks: `lvs -o lv_name,lv_size,data_percent --sort -data_percent pve | head`.
3. `qm list`: old templates (the golden images are VMs 9000-9003; an aborted image build
   can leave builder VM 9009), forgotten workstations.

## Common causes

- Many workstations, each writing to its own thin disk.
- Leftover images: `lab image build` removes the previous image only when the new one
  succeeds.
- Backups go to `local`, not `local-lvm`: they don't cause this.

## Escalate / fix

- Remove machines nobody needs through the admin page (it also cleans up AD, DHCP and DNS).
- Never `lvremove` a VM disk by hand, and never `qm destroy` a machine the portal or
  OpenTofu tracks: their records and states would point at nothing.
- Growing the pool starts on the Windows host (pve01's virtual disk in Hyper-V), then
  `pvresize` and `lvextend` on pve01. Plan it; it isn't a five-minute fix.
