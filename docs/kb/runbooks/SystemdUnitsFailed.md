# SystemdUnitsFailed

## What it means

At least one systemd unit on the machine has been `failed` for 5 minutes. One alert per
machine (the value is the number of units), so a template unit failing a thousand times
doesn't bury every other alert. The list is on the Machine dashboard
(https://lab.radicallydecent.com/grafana/d/lab-machine/machine?var-host=&lt;host&gt;, panel "Failed systemd units").

```promql
count by (host) (node_systemd_unit_state{state="failed"} == 1)
```

## First five minutes

1. `systemctl --failed` on the host (workstations: on pve01,
   `qm guest exec <vmid> -- systemctl --failed`).
2. For each: `systemctl status <unit>` and `journalctl -u <unit> -b -n 50`.
3. Many units with the same template name (`name@...`) are one cause repeated: read one.
4. Is it still happening? `journalctl -u '<name>@*' --since -10min | tail`.

## Common causes

- Template units started once per connection that fail and stay listed
  ([per-connection-unit-pileup](../patterns/per-connection-unit-pileup.md)).
- Two mechanisms configured to start the same daemon
  ([conflicting-activation-modes](../patterns/conflicting-activation-modes.md)).
- Hardware or kernel units that can't work inside the mgmt01 container
  ([container-irrelevant-units](../patterns/container-irrelevant-units.md)).
- A unit that ran too early at boot ([boot-ordering-race](../patterns/boot-ordering-race.md)).

## Escalate / fix

- Fix the cause in the role that owns the unit (the unit file's header names it), then
  `systemctl reset-failed <unit>` so the state tells the truth. `reset-failed` alone
  only hides the problem until it fails again.
- A unit that can't apply to a host: mask it in that host's role, with a comment why.
