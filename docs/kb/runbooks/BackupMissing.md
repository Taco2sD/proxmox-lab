# BackupMissing

## What it means

A server the nightly backup job covers (dc01, VM 105; mgmt01, CT 106) has no backup from
the last 26 hours, or has never been backed up. Or the collector that reports backups
(lab-backup-metrics on pve01) has stopped, so nobody can tell. The job runs at 03:30
(roles/pve_backups); a day-old miss means last night's run didn't produce an archive.

Nothing is broken for users yet. What's at risk is recovery: dc01 holds the AD database,
mgmt01 the OpenTofu state, guest records, passwords and keys. Neither can be rebuilt
from git.

## First five minutes

1. What exists, on pve01: `pvesh get /nodes/pve01/storage/local/content --content backup`
   (newest first by `ctime`), or `ls -lt /var/lib/vz/dump/`.
2. Did last night's job run, and how did it end: `pvesh get /nodes/pve01/tasks --typefilter vzdump --limit 5`,
   then the log next to the archive (`/var/lib/vz/dump/vzdump-*-<date>.log`).
3. Is the job still there and enabled: `pvesh get /cluster/backup --output-format json`
   (id `lab-servers`, schedule 03:30, vmid 105,106).
4. Is the collector running: `systemctl status lab-backup-metrics.timer lab-backup-metrics.service`
   and `cat /var/lib/prometheus/node-exporter/lab-backups.prom`.
5. Space on the backup storage: `pvesm status` (local).

## Common causes

- The job ran but a guest failed: the snapshot couldn't be taken (guest agent hung in
  fs-freeze on dc01; a stale `vzdump` snapshot left on CT 106), or the storage filled up.
- The job was disabled or edited by hand in the Proxmox UI (the reconciler puts the
  schedule and guest list back on its next full run; other settings it doesn't check).
- pve01 was off or the lab host asleep at 03:30: a missed schedule isn't caught up.
- The collector stopped (failed unit, missing python3, node_exporter's textfile
  directory gone): the alert's second half fires with no guest named.

## Escalate / fix

- Take a backup now, the same way the job does: `vzdump 105 106 --storage local --mode snapshot --compress zstd`
  (dc01 about 15 s, mgmt01 about 30 s; both stay running). Then re-run
  `systemctl start lab-backup-metrics.service`; the alert clears within a scrape.
- If a snapshot is stuck: `pct unlock 106` / `qm unlock 105` only after confirming no
  vzdump is running (`pgrep -a vzdump`).
- Never test a restore over the real guests. Restore into a throwaway ID with
  `--unique 1`, remove its network before it could start (`qm set <id> --delete net0`),
  and never start a copy of dc01: two domain controllers with one identity on the network
  corrupt AD. KB-0100 has the tested steps.
