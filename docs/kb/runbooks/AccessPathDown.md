# AccessPathDown

## What it means

A workstation is up (Prometheus still scrapes its node_exporter), but one of the ways
people reach it has failed its probe for 3 minutes. The `probe` label says which:

| probe | checks | served by |
|---|---|---|
| SSH | `<workstation>:22` answers with an `SSH-2.0-` banner | `ssh.service` on the workstation; the browser terminal (Guacamole) uses the same path |
| Desktop console | `10.10.10.10:<6000 + VM ID>` answers with an `RFB 003` banner (desktop machines only) | `lab-console.socket` on pve01 (ansible/roles/pve_console), then `qm vncproxy` and the VM's QEMU VNC server |

The targets come from lab-metrics (`/etc/lab-monitoring/prometheus/targets/access.json` on
mgmt01): every running, ready workstation gets an SSH probe, desktop machines also a
console probe. Job `probes-access`, every 60 seconds; modules `ssh_banner` and
`rfb_banner` in ansible/roles/monitoring/templates/blackbox.yml.j2. Neither probe logs
in or completes a VNC handshake, so a failure is about the path, not credentials.

A machine that is down altogether raises [TargetDown](TargetDown.md) instead; hibernated
or stopped machines aren't probed at all.

## First five minutes

1. Which machine and path: Lab overview, Workstations row, "Access paths" panel; or
   `probe_success{job="probes-access"} == 0` at https://lab.radicallydecent.com/prometheus/.
2. Re-run the probe with its log, on mgmt01:
   `curl -s 'http://127.0.0.1:9115/probe?module=ssh_banner&target=10.10.10.36:22&debug=true'`
   (or `module=rfb_banner&target=10.10.10.10:6136` for a console).
3. SSH: from mgmt01, `timeout 3 bash -c 'exec 3<>/dev/tcp/<ip>/22; head -c 20 <&3'`.
   Then on the machine (through pve01 if SSH itself is the problem):
   `qm guest exec <vmid> -- systemctl status ssh --no-pager`.
4. Desktop console: on pve01, `journalctl -u 'lab-console@*' --since -10min --no-pager`
   (a running VM should show `Deactivated successfully` per probe), `systemctl status
   lab-console.socket`, and `qm status <vmid>`.

## Common causes

- sshd stopped or failed on the workstation (a bad sshd config from a configuration run:
  `journalctl -u ansible-pull -n 50` on the machine).
- The machine is booting or shutting down slowly enough to outlast 3 minutes with
  node_exporter up (rare; it clears by itself).
- Console relay: `lab-console.socket` stopped on pve01, the console secret missing
  (`/etc/lab/console.env`), or the VM's QEMU process gone while Proxmox still reports
  it running. The relay refuses VMs that aren't running on purpose (KB-0001's fix): if
  the VM *is* running and it still refuses, compare `/var/run/qemu-server/<vmid>.pid`
  with `qm status <vmid>`.

## Escalate / fix

- SSH: `qm guest exec <vmid> -- systemctl restart ssh`, then watch the panel recover.
  If the configuration run broke it, fix the role and let the next pull repair it.
- Console relay: `systemctl restart lab-console.socket` on pve01 (it only affects new
  Desktop connections). Never restart pve-cluster or pveproxy for this.
- Don't hibernate or stop the machine to "fix" it: it would just drop out of the probe
  list and hide the problem.
