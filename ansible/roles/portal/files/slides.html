Linux workstation lab

Prototype of a self-service Linux workstation platform for a studio: a domain-joined workstation on request, in a few minutes. Built in four days on a single Windows PC.

What’s running

pve01Proxmox VE, nested in Hyper-V. Hosts dc01, mgmt01 and the workstations.
dc01Samba Active Directory domain controller, plus DNS and DHCP.
mgmt01LXC container: self-service portal, automation (Ansible, OpenTofu), Prometheus, Grafana, Guacamole.
WorkstationsUbuntu desktops and headless dev boxes, in seven roles.
VPSPublic entry point with the sign-in page. The lab connects out to it over WireGuard and accepts no inbound connections.

Requesting a workstation

A role is picked on the self-service portal. A few minutes later:

  1. AD user and computer accounts are created.
  2. A DHCP reservation and DNS record give it a fixed address and name.
  3. Proxmox clones the golden image, sized for the role.
  4. On first boot it joins the domain by itself.
  5. Ansible applies the role’s packages and settings.
  6. It opens in the browser via Guacamole (terminal or desktop), or over SSH.

Requests are checked against a memory budget and a cap of 12 machines, and every action is logged. New hires can onboard themselves with a one-time sign-up link.

What happens automatically

  • Domain join with a one-time password. No admin credentials on the workstation.
  • DNS records follow DHCP: created with the lease, removed when the machine is deleted.
  • Configuration comes from the machine’s role (an AD group), re-applied by ansible-pull every 30 minutes.
  • Monitoring discovers new machines within a minute, including SSH and desktop checks.
  • Hibernated or deleted machines drop out of monitoring without false alarms.
  • Idle machines hibernate after 48 hours to free memory.
  • Deleting removes the VM, AD accounts, DHCP reservation and DNS records in one step.

Monitoring

  • Lab overview in Grafana: alerts, service checks, memory and disk across all machines.
  • Per-machine dashboard: VM or container, the CPU and memory limits Proxmox sets, and its share of the host’s disk.
  • Service checks test the portal, Guacamole, AD, DNS and the sign-in page the way a user would.
  • Every alert links to a runbook. CI rejects an alert rule without one.

From commit to running lab

push → CI → stable branch → reconciler on mgmt01 → Ansible and OpenTofu

  • Git is the source of truth: servers, workstation fleet and roles, dashboards, alert rules and runbooks.
  • CI on GitHub Actions checks every push to main and every pull request. Only passing commits are promoted to stable; main is never deployed.
  • Pull-based (GitOps): the reconciler and the workstations’ ansible-pull fetch stable and apply it. GitHub can’t reach into the lab.
  • Continuous deployment with one manual gate: deleting or replacing a VM needs an admin’s approval.

CI checks and the reconciler

CI

  • yamllint, ansible-lint, shellcheck, ruff
  • Python unit tests
  • Inventory rules: names, VM ID ranges, addresses, no duplicates, roles exist
  • OpenTofu fmt and validate
  • All checks run; every failure is reported in one pass

Reconciler (systemd timer, every minute)

  • New commit on stable: Ansible for the servers, then OpenTofu for the VMs
  • VMs re-applied every 30 minutes to correct drift; idempotent, so safe to repeat
  • A failed commit isn’t retried every minute
  • Locked against overlapping runs; can be paused for maintenance

Knowledge base

  • 71 issues found during the build, each with cause, fix and verification.
  • Example: reloading Docker containers with a signal marked them as manually stopped, so monitoring stayed down after a reboot.
  • Example: the first failed-service alert rule fired about 1,700 alerts at once.
