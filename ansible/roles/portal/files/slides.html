Linux workstation lab

Prototype of a self-service Linux workstation platform for a studio: a domain-joined workstation on request, in a few minutes. Built in four days on a single home workstation.

What’s running

pve01Proxmox VE, nested in Hyper-V on a Windows home workstation. Hosts dc01, mgmt01 and the workstations.
dc01Samba Active Directory domain controller, plus DNS and DHCP.
mgmt01LXC container: self-service portal, automation (Ansible, OpenTofu), Prometheus, Grafana, Guacamole.
WorkstationsUbuntu desktops and headless dev boxes. Seven roles (artist, programmer, audio and so on), each with its own software and VM size.
VPSAn existing VPS that already hosts a website, reused as the public entry point and sign-in page. The lab connects out to it over WireGuard, so nothing at home is exposed to the internet.

Requesting a workstation

A role is picked on the self-service portal. A few minutes later:

  1. AD user and computer accounts are created.
  2. A DHCP reservation and DNS record give it a fixed address and name.
  3. Proxmox clones the golden image, sized for the role.
  4. On first boot it joins the domain by itself.
  5. Ansible applies the role’s packages and settings.
  6. It opens in the browser via Guacamole (terminal or desktop), or over SSH.

New hires can set up their own account and workstation from a one-time sign-up link. Since everything shares one host, requests are capped by available memory and a 12-machine limit.

What happens automatically

  • Domain join uses a one-time machine password, so no admin credentials reach the workstation.
  • DNS records follow DHCP: created with the lease, removed when the machine is deleted.
  • Configuration comes from the machine’s role (an AD group) and is re-applied by ansible-pull every 30 minutes, which corrects drift.
  • Monitoring discovers new machines within a minute, including SSH and desktop checks.
  • Hibernated or deleted machines drop out of monitoring without false alarms.
  • Idle machines hibernate after 48 hours to free memory.
  • Deleting removes the VM, AD accounts, DHCP reservation and DNS records in one step.

Monitoring

  • Lab overview in Grafana: alerts, service checks, memory and disk across all machines.
  • Per-machine dashboard: CPU, memory and disk use against the limits Proxmox sets for it.
  • Service checks test the portal, Guacamole, AD, DNS and the sign-in page the way a user would.
  • Every alert links to a runbook. CI rejects an alert rule without one.

From commit to running lab

push → CI → stable branch → reconciler on mgmt01 → Ansible and OpenTofu

  • Git is the source of truth: servers, workstation fleet and roles, dashboards, alert rules and runbooks.
  • CI (GitHub Actions) runs linters, unit tests and inventory validation on every push to main. Only commits that pass are promoted to stable, the branch the lab runs.
  • Pull-based (GitOps): a systemd timer on mgmt01 checks stable every minute and applies new commits. Workstations pull stable themselves with ansible-pull every 30 minutes. GitHub never connects to the lab.
  • One owner per piece: OpenTofu creates and sizes the VMs (clone, CPU, memory, disk). Ansible configures the servers, everything inside each workstation, and its AD and DHCP entries.
  • Continuous deployment with one manual gate: deleting or replacing a VM needs an admin’s approval.

Knowledge base

  • Every issue hit during the build is documented in the repository: 71 entries, each with cause, fix and how the fix was verified.
  • Example: reloading Docker containers with a signal marked them as manually stopped, so monitoring stayed down after a reboot.
  • Example: the first failed-service alert rule fired about 1,700 alerts at once.
