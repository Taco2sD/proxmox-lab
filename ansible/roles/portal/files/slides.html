Linux workstation lab

A prototype of a self-service workstation platform for a studio’s IT team. Built in four days on one Windows PC.

What’s running

pve01Proxmox VE, nested in Hyper-V. Hosts everything below.
dc01Samba Active Directory domain controller. Also DNS and DHCP.
mgmt01Management container: the portal, the automation, Prometheus, Grafana, Guacamole.
WorkstationsUbuntu desktops and headless dev boxes, built on request. Seven roles.
VPSThe public entry point with the sign-in page. Connects in over a WireGuard tunnel; the lab itself accepts no inbound connections.

Requesting a workstation

Someone picks a role on the portal. A few minutes later:

  1. An AD user account and computer account are created.
  2. A DHCP reservation gives it a fixed address and name.
  3. Proxmox clones the golden image, sized for the role.
  4. On first boot it joins the domain by itself.
  5. Ansible applies the role’s packages and settings.
  6. It opens in the browser (terminal or desktop via Guacamole), or over SSH.

Each request is checked against a memory budget and a cap of 12 machines. The admin page logs every action. New hires can also onboard themselves at /welcome with a one-time sign-up link.

What happens automatically

  • Domain join with a one-time password. No admin credentials ever go on the machine.
  • DNS records are created from the DHCP lease and removed when the machine is deleted.
  • Configuration comes from the machine’s AD group. It re-checks against git every 30 minutes.
  • Monitoring picks up new machines within a minute, with SSH and desktop checks. No manual setup.
  • Hibernated or deleted machines drop out of monitoring without false alarms.
  • Idle machines hibernate after 48 hours to free memory.
  • Deleting removes the VM, AD accounts, DHCP reservation and DNS records together.

Monitoring

  • Lab overview in Grafana: alerts, service checks, memory and disk, every machine.
  • Machine page: shows whether it’s a VM or a container, the CPU and memory limits Proxmox puts on it, and how much of the host’s disk it uses.
  • Service checks test the portal, Guacamole, AD, DNS and the sign-in page the way a user would.
  • Every alert links to a runbook. CI rejects an alert rule that doesn’t have one.

How a change reaches the lab

push → tools/check → stable → reconciler, within a minute → Ansible and OpenTofu make the lab match

  • CI: every push to main and every pull request runs tools/check on GitHub Actions. It’s the same script you run locally.
  • Promotion: CI fast-forwards stable only to commits that passed. main is checked but never deployed.
  • Pulled, not pushed: git holds the desired state. The reconciler on mgmt01 and the workstations’ ansible-pull fetch stable and apply it. GitHub can’t reach into the lab.
  • Continuous deployment: a commit that passes goes live without anyone pressing deploy. One human step: destroying a machine waits for an admin’s approval.
  • Dashboards, alert rules and runbooks are in the same repo and deploy the same way.

What each step does

tools/check, on every push

  • Eight groups: yamllint, ansible-lint, shellcheck, ruff and the unit tests, inventory rules, broken path references, the knowledge base, OpenTofu fmt and validate.
  • set -uo pipefail without -e: it runs every group even after one fails, then lists all the failures together.
  • Any failure exits 1, and stable doesn’t move.

lab reconcile, every minute on mgmt01

  1. Skips the run if paused, or if another run holds the lock.
  2. Fetches stable and compares it with the last deployed commit.
  3. If it moved: site.yml for the servers, then OpenTofu for the VMs.
  4. Every 30 minutes it applies the VMs anyway, which repairs drift. Safe to repeat.
  5. A commit that failed isn’t retried every minute, only every 30 minutes.
  6. Destroying or replacing a VM waits for an admin.

What I learned

  • Every problem found while building it is written up in the knowledge base: 71 issues, each with cause, fix and proof.
  • Example: reloading Docker containers with a signal marked them as manually stopped, so monitoring stayed down after a reboot.
  • Example: the first “failed service” alert rule fired about 1,700 alerts at once.
