Linux workstation lab

A working prototype of self-service Linux workstations for a studio. Staff request a machine in the browser and get a ready, domain-joined workstation a few minutes later. Built in four days on one Windows PC.

What’s running

pve01Proxmox VE, running inside Hyper-V on the PC. Hosts all the machines below.
dc01Samba Active Directory domain controller, also DNS and DHCP.
mgmt01Management container: the self-service portal, the automation, monitoring (Prometheus and Grafana) and browser access to the machines (Guacamole).
WorkstationsUbuntu desktops and headless development machines, in seven roles such as artist, audio, programmer and infrastructure.
Public serverA small cloud server with the sign-in page. The lab connects out to it over WireGuard, so nothing on the internet can reach the lab directly.

Requesting a workstation

A staff member signs in to the portal and picks a role. A few minutes later:

  1. Their Active Directory account and the machine’s computer account exist.
  2. The machine has a reserved address and a DNS name.
  3. Proxmox has cloned a prepared base image, sized for the role.
  4. On first boot, the machine joins the domain by itself.
  5. Ansible installs the role’s software and settings.
  6. It opens in the browser, as a terminal or a full desktop, or over SSH.

New hires get a one-time link to set up their own account and first workstation. Requests are capped so the host can’t run out of memory, and an admin page records every action.

What happens automatically

  • Domain join uses a one-time password. No admin credentials are ever stored on a workstation.
  • DNS records are created when a machine gets its address and removed when it’s deleted.
  • Software and settings follow the machine’s role and are re-applied from git every 30 minutes, so manual changes don’t stick.
  • Monitoring picks up a new machine within a minute, with no manual setup.
  • Hibernated or deleted machines leave monitoring without false alarms.
  • Idle machines hibernate after 48 hours to free memory.
  • Deleting a machine removes its VM, AD accounts, address reservation and DNS records together.

Monitoring

  • Lab overview in Grafana: active alerts, service health, and memory and disk for every machine.
  • One dashboard per machine: CPU, memory and disk use, next to the limits Proxmox gives it.
  • Service checks use the portal, browser access, AD, DNS and the sign-in page the way a user would.
  • Every alert links to a runbook that says what to do. An alert without one can’t be deployed.

How a change reaches the lab

Commit to git → automated checks → release branch → the lab applies it within a minute

  • Git is the source of truth. The servers, the workstation roles, the dashboards and the alerts are all defined in one repository.
  • Every change is checked on GitHub Actions. Only changes that pass move to the release branch, stable, which is what the lab runs.
  • The lab pulls changes; nothing pushes into it. GitHub holds no credentials and can’t reach the lab.
  • No deploy button. A change that passes goes live on its own. Deleting or replacing a machine waits for an admin’s approval.

The checks and the deployment

Checks on every change

  • Linting for YAML, Ansible, shell scripts and Python.
  • Unit tests for the portal and the automation.
  • Machine and role definitions: valid values, nothing used twice.
  • Validation of the OpenTofu code that defines the VMs.
  • One run reports every failure, not just the first.

On the lab, every minute

  • A service on mgmt01 checks the release branch for a new commit.
  • If there is one, Ansible configures the servers, then OpenTofu creates or changes the VMs.
  • Every 30 minutes the VMs are re-applied anyway, undoing manual changes.
  • A commit that failed isn’t retried every minute.
  • Only one run at a time, and it can be paused for maintenance.

What I learned

  • I wrote up every problem I hit while building it: 71 so far, each with its cause, the fix and how the fix was verified.
  • Example: restarting the monitoring containers the wrong way made Docker treat them as stopped by hand, so monitoring didn’t come back after the host rebooted.
  • Example: the first alert rule for failed services fired about 1,700 alerts at once.
